# User Stories und Kanban

Die in [user_stories_mvp1.md](../02_mvp/user_stories_mvp1.md) beschriebenen Stories bilden den geplanten Backlog. Für die Tag-03-Abnahme müssen sie im **eigenen** GitHub-Repository als Issues erfasst und einem Projekt zugeordnet sein. Ein vorhandenes Konzeptdokument allein beweist das nicht.

## Board-Struktur

Das Board verwendet die Spalten **Backlog**, **To Do**, **In Progress**, **Code Review / Testing**, **Ready for Deployment** und **Done**; **Blocked** ist optional. Jede Story erhält Akzeptanzkriterien, eine verantwortliche Person und einen Bezug zum Epic. Parallel begonnene Arbeit wird begrenzt; nur getestete und ausgelieferte Aufgaben kommen nach Done.

## Issues erfassen

Im Repository `itcne25/techstyle` zuerst vorhandene Issues prüfen, damit keine Dubletten entstehen. Dann Epic und Stories aus dem Konzept übernehmen, Labels sinnvoll setzen und dem eigenen Projekt zuordnen. Die früheren zwei Automationsskripte waren teilweise auf `tbzdevops/techstyle` bzw. fremde Projektnummern festgelegt und wurden entfernt. Ihr Ausführen war kein Teil der Bereinigung.

Die Projekt-URL und die echten Issue-Links nach dem Anlegen hier ergänzen. Dasselbe gilt für den tatsächlich versendeten Marketingfeedback-Entwurf. Es werden keine Links oder abgeschlossenen Arbeitsschritte erfunden.
